# Изоляция локального входа и публичной статики

Обычный `GET`/`HEAD /` с IP в Host получает `303 Location: /?login` без
контакта с control/site DB и без reverse proxy. Неизвестный локальный `localhost`
при прямом loopback-соединении использует тот же вход. Опубликованный `localhost`
обслуживается по его публичной политике. При отсутствии публичной политики
корневой URL больше не запускает восстановление публикации через SQL.

Вход не утверждает, что администратор существует, и не даёт локальных прав.
`?login` определяет владельца один раз на динамическом ingress; SQL-проверки
владельца и наличия администратора ограничены двухсекундным deadline на границе
SQL. Ошибка возвращает 503. Только подтверждённое отсутствие администратора
позволяет перейти к регистрации. Внешняя установка по IP сохраняет HTTPS,
install code и проверки первого владельца; поддельный Host/forwarding header
не превращает внешний запрос в локальный.

До исправления каждый проблемный запрос выполнял как минимум один callback
control DB (`ip-owner-domain`) и один запрос site DB (`COUNT users`). Дополнительно
могли выполняться проверки состояния удаления. Эти операции последовательно
ждали ограниченных DB-воркеров. До очередей не было ограничения числа ожидающих
HTTP handlers. Значения `proxy_backend` и `first_write` включали это ожидание;
малое `body_write` само по себе не измеряло работу SQL.

## Границы ресурсов

Один Front допускает 64 активные динамические сессии суммарно для HTTP и HTTPS.
Приложение имеет собственный такой же предел до динамических middleware,
включая приватный Test Drive и операции восстановления/оплаты. Дополнительного
HTTP ожидания допуска нет: переполнение возвращает 503, `Retry-After: 1` и
`Cache-Control: no-store`. Долгие WebSocket/streaming операции занимают допуск
до своего завершения. Публичная статика не занимает эти контакты.

Автоматическая аналитика посетителей (`/?request=analytics`, WebSocket и POST
beacon) имеет отдельный лимит 128 контактов в Front и приложении. Она не
занимает 64 административных контакта. Лимит активных аналитических соединений
в обработчике приложения сохраняется. Смешанные query-селекторы не получают
допуск аналитики: административные маршруты сохраняют собственный лимит.

Очереди DB сохраняют прежние размеры и число работников. Переполнение очереди
возвращает ошибку вместо ожидания свободного места вне очереди. Отмена до
handshake исключает выполнение callback; отменённое сообщение пропускается
работником при извлечении. После handshake вызывающий ждёт возврата владения
через reply. Уже принятая операция не объявляется завершённой до фактического
завершения callback; отмена поступает к SQL через его библиотечную границу.

## Диагностика

`--request-timings` или `--profiler` включает неблокирующий сбор наблюдений.
Каждые 30 секунд строки `REQUEST TIMING` содержат начало/конец интервала,
число наблюдений, `statuses`, среднее, p50/p95/p99 и точный максимум интервала.
Перцентили отмечены `_upper`: это верхние границы гистограммы. Счётчики
профилировщика остаются накопительными; его записи используют разность снимков.
Не складывать данные разных процессов или несовпадающих интервалов.

| Стадия | Наблюдение |
| --- | --- |
| `public_static_ram` | Готовый публичный RAM-ответ |
| `public_static_file` | Публичный путь с файловым fallback, включая отказы политики/отсутствующие файлы |
| `unknown_host` | Терминальный отказ неизвестному Host |
| `local_ip_entry` | Детерминированный вход по IP/локальному localhost |
| `proxy_application` | Динамический путь, включая отказ допуска |
| `control_db_queue` / `site_db_queue` | Ожидание от подачи до handshake, либо до отмены/отказа |
| `control_db_execution` / `site_db_execution` | Работа принятого DB callback без ожидания очереди |

У DB стадий `statuses` обозначают исход операции: 200 — выполнена, 499 —
отменена, 503 — не допущена/недоступна, 500 — ошибка выполнения. Это не HTTP-ответы.
Один control callback может содержать несколько SQL statements. Site DB
наблюдение заканчивается при возврате результата SQL вызова; последующее чтение
`sql.Rows` вызывающим сюда не входит. Наблюдения учитываются при завершении,
поэтому операция через границу интервала относится к интервалу завершения.
При переполнении диагностического канала запрос не ждёт: интервал помечается
`incomplete`, выводится минимально известное число потерянных наблюдений.

## Регрессии и окончательная проверка

```sh
CGO_ENABLED=0 go test . ./pkg/publicsite ./pkg/requesttiming ./scripts/architecture \
  -run 'TestLoopbackEntry|TestLocalIPEntry|TestLocalAccountControlError|TestAccountDatabaseErrors|TestDatabaseQueueOverflow|TestCanceledControlQueue|TestBackendAdmission|TestIntervals|TestRouteLatency|TestOwnership' \
  -count=1 -timeout=3m
```

Регрессия поднимает HTTP и HTTPS с одним Front, удерживает все динамические
контакты канальным барьером, одновременно проверяет локальный вход, неизвестный
Host и правильное содержимое опубликованного HTTPS сайта. Отдельные тесты
проверяют отсутствие SQL, ошибки аккаунта, переполнение и отмену до/после
передачи владения. Порядок задаётся каналами, `time.Sleep` не используется.

Production нагрузка и финальная проверка OpenBSD остаются владельцу сервера.
Для проверки корневого IP не следовать редиректам (`curl` без `-L`): отдельный
запрос к `?login` намеренно выполняет динамическую проверку аккаунта. Сравнивать
статусы и задержки по одному 30-секундному интервалу и проверять опубликованный
домен с правильным SNI/Host одновременно с потоком запросов на loopback.
