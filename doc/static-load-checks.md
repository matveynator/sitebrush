# Статическая отдача и нагрузочная проверка

Обычный гостевой GET/HEAD опубликованной страницы, файла и URL с UTM-параметрами
не обращается к SQL. Правила домена, алиасов, паролей, файлов и доверия IP
обслуживает отдельный канальный участник. Отсутствующая страница получает 404.
Вход, разблокировка раздела, загрузки по токенам, генерируемые robots/sitemap
при отсутствии готовых файлов и действия редактора сохраняют
свою проверку доступа. Первый запуск на localhost переводит на регистрацию.

При публикации изменяются файл и снимок правил. Перед изменением защиты
подтверждается блокировка старого снимка; после записи подтверждается новый.
Обновление приложения сохраняет публичные HTTP/HTTPS listeners. Для правил без
проверки файлов при каждом запросе нужно обновить и перезапустить launcher
вместе с приложением. Старый launcher/child продолжает безопасную проверку
правил с диска. При превышении ограниченного кэша также сохраняется этот режим.

Маленький асинхронный загрузчик размещается в начале HTML, с сохранением doctype,
и не ждёт скриптов самой страницы. Полный код меню загружается после первого
открытия с высоким приоритетом. Аналитика загружается после
события `load`, в свободное время браузера. Гостевая выдача HTML не ждёт очереди
рендеринга и не собирает полное тело страницы в памяти. Служебные события
сериализуются отдельным участником и передаются пакетами через постоянную
NetChan-сессию. Пакет сохраняется до подтверждения потребителем. При перегрузке
пропускаются более поздние события, а отчёт отмечается как неполный.

## Ручная проверка

1. Войдите с IP, с которого будете запускать `ab`, либо добавьте IP/CIDR в
   разрешённые адреса администратора. IP владельца сервера освобождается от
   автоматических ограничений нагрузки на всех сайтах установки; IP
   администратора отдельного сайта — только на этом сайте. Подтверждённый вход
   действует в пределах существующего срока доверия (90 дней), явно добавленное
   правило — до удаления. Исключение не открывает редактор и закрытые файлы.
2. Запустите без cookies для своего опубликованного сайта:

   ```sh
   ab -k -t 30 -c 300 'https://your-domain.example/'
   ab -k -t 30 -c 600 'https://your-domain.example/'
   ab -k -t 30 -c 1000 'https://your-domain.example/'
   ab -t 30 -c 300 'https://your-domain.example/'
   ```

   Повторите для HTTP, вложенной страницы, алиаса и картинки. Для изображения
   используйте его настоящий `/p/…` URL. Проверьте `Failed requests`, ответы
   429/503 и показатели `Waiting`/`Total`. Более 300 соединений разрешено;
   фактический предел зависит от ресурсов сервера и тестового клиента.
3. На публичном сайте откройте меню сразу после появления страницы, на
   компьютере и телефоне. До ответа сервера должно быть «Проверяем вход…», затем
   в приватном окне — пункт входа, а в окне с действующей сессией — полное меню.
   Меню должно иметь обычные стили и фиксированное положение. Если WebSocket
   недоступен, показывается ошибка проверки входа; повторное открытие повторяет
   запрос. При обычном просмотре инструменты браузера должны показывать загрузку
   аналитики после `load`, а загрузку `guest_menu.*.js` — при открытии меню.
   Дополнительно замедлите сторонний скрипт страницы в инструментах браузера:
   меню должно открываться до завершения его загрузки, в том числе пока
   `document.body === null`. В приватном окне должен появиться пункт входа,
   с действующей сессией — полное меню без ошибки вставки в `body`.
4. Заморозьте сайт, измените страницу и опубликуйте. Гостевой просмотр должен
   показывать опубликованную версию. Повторите просмотр во время обновления
   программы: уведомление об обновлении появляется только в контекстном меню.
5. Проверьте страницу и файл под паролем в приватном окне. Удалите доверенный IP
   и проверьте, что автоматическая защита снова действует; доверие администратора
   одного сайта не должно распространяться на чужой сайт.
6. После нагрузки откройте аналитику. Сохранённые наблюдения остаются; при
   пропусках показывается неполнота. Их отсутствие не должно отображаться как
   доказанное отсутствие посетителей.
7. В учётной записи включите нужные AI-доступы, сохраните и перезагрузите
   страницу. Значения должны сохраниться без `Forbidden`. Затем подключите
   `https://ваш-домен/?mcp` в ChatGPT, войдите в SiteBrush и подтвердите доступ.
   Ожидается возврат в ChatGPT без `invalid_client`. Попросите изменить конкретную
   страницу в черновике, проверьте её и отдельно попросите опубликовать. На
   публичном демо разрешение владельца не требуется.
   На обычном сайте через launcher запросы MCP с публичным Host должны работать
   и на внутреннем loopback-соединении. Повторите запрос аналитики безопасности
   через подключённый коннектор. В журнале домена должна появиться строка `MCP`
   с HTTP-статусом, адресом клиента и результатом, без токенов и текста страницы.
8. Откройте страницу под паролем с действующей сессией администратора, файл по
   токену и генерируемые `robots.txt`/`sitemap.xml`. Один запрос должен давать одну
   техническую запись, без удвоения событий безопасности и счётчика 404.
9. Если установка уже использует чтение правил с диска из-за размера каталога,
   повторите нагрузку с IP владельца сервера на другом сайте и его алиасе.
   Исключение должно работать сразу, без предварительного посещения сайта
   владельца; удаление этого IP должно отзывать исключение на всех сайтах.
10. После запуска проверьте AutoCert. Сертификаты удалённых сайтов сохраняются
    в кэше, но не запускают обновление без существующего сайта или активной
    регистрации. Для настоящей ошибки журнал содержит `AUTOCERT stage=… error=…`
    и время следующей попытки; один `storage_error` больше не скрывает причину.

Последние исправления меню, AI-настроек, OAuth и режима чтения правил с диска
подготовлены 24 октября. По просьбе владельца повторные локальные прогоны для
них не выполнялись. Успешное подключение настоящего ChatGPT к рабочему серверу
остаётся отдельной ручной проверкой после установки сборки с этими изменениями.

## Локальные измерения

23 октября 2026, macOS/arm64, Apple M1, CGO отключён. Сравнение с `main` на
коммите `3ced772`, страница около 100 КБ, настоящие HTTP-запросы и keep-alive.
В исходном варианте обычная отдача использовала прогретый HTML-кэш; сценарий
`stalled` оставлял очередь рендеринга без потребителя и заполнял очередь аналитики.
Новый вариант использует потоковую отдачу и снимки правил в памяти.

Медианы трёх прогонов `-benchtime=1s`. TTFB включает локальный клиент и соединение;
это нагрузка до насыщения, а не ограниченная одинаковым RPS нагрузка.

| Соединения / режим | Запросы/с, до → после | TTFB p50, мс | p95, мс | p99, мс |
|---|---:|---:|---:|---:|
| 300 / обычный | 7 606 → 15 895 | 38,9 → 11,9 | 45,6 → 49,8 | 49,0 → 75,0 |
| 300 / stalled | 4 624 → 15 044 | 64,5 → 12,8 | 72,0 → 52,6 | 78,9 → 87,5 |
| 600 / обычный | 7 386 → 12 780 | 79,9 → 33,8 | 86,4 → 88,6 | 103,0 → 139,9 |
| 600 / stalled | 4 713 → 12 773 | 124,1 → 34,5 | 137,3 → 96,9 | 148,6 → 163,9 |

Типичный первый ответ и пропускная способность улучшились. p99 под предельной
нагрузкой в этом замере вырос; улучшение хвостовой задержки не заявляется.
Внутренний обработчик без сети: около 69 → 41 мкс, 111 → 71 выделение памяти
на запрос (новый вариант включает подготовленную конфигурацию корня хранилища).
Эти числа не описывают скорость рабочего сервера или WAN/TLS.

Повторить HTTP-замер:

```sh
CGO_ENABLED=0 go test . -run '^$' -bench '^BenchmarkPublicHTTP$' -benchmem -benchtime=1s -count=3
```

Основные автоматические проверки охватывают SQL-независимую выдачу при 600
одновременных запросах, отзыв IP, ограничения сайтов, пароли, Range/HEAD/304,
снимки правил, подтверждение пакетов, совместимость launcher и обновление/откат.
Chromium проверяет отложенную загрузку и меню на desktop/mobile. HTTPS проверен
функционально; нагрузочную проверку HTTPS рабочего сервера выполните отдельно.
